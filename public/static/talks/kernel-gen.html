the question

Can LLMs
write kernels?

Two years ago: clearly not. Today: a 33-slide answer.

primer

What's a GPU kernel?

  • A small program that runs on the GPU — one piece of work, many threads.
  • Every PyTorch op — x @ y, softmax(x), F.scaled_dot_product_attention — eventually dispatches to a kernel.
  • The kernel is where the performance lives. The Python layer just decides which kernel to call.
  • Writing one well means thinking about memory, occupancy, tile sizes, register pressure, instruction-level parallelism.
// dispatch chain
# PyTorch — one line
y = F.softmax(x, dim=-1)

# Underneath: a CUDA / Triton kernel

motivation

Why this is worth automating

— from the KernelBench blog, Stanford SAIL

  • FlashAttention is the obvious example. One well-tuned kernel, used in basically every transformer trained today.
  • Expert kernel engineers are scarce. Hand-tuning one kernel: weeks.
  • Hardware moves faster than humans can re-tune. Every new chip resets the clock.
// why automation looks tractable

Programs are short, usually 50–500 lines. Evaluation is mechanical: did it match, was it faster. Compile errors, unit tests, and the profiler all give signal. On paper, a near-perfect target for code-gen and RL.

PART II · Where this started

KernelBench

The first benchmark for "can a model write a faster kernel than PyTorch?"

● Stanford SAIL · Dec 2024 · 250 tasks · 3 levels
II.1 — task structure

Three levels of difficulty

Each task: a PyTorch nn.Module. Goal: write a faster CUDA kernel that produces matching outputs.

Level 1 · 100 tasks

Single ops — matmuls, convs, layernorm.

Level 2 · 100 tasks

Fusion patterns — conv + bias + ReLU. One kernel beats three.

Level 3 · 50 tasks

Full architectures — MobileNet, VGG, MiniGPT. Optimize the whole network.

Ouyang et al. KernelBench: Can LLMs Write GPU Kernels? Stanford SAIL, Dec 2024 · arXiv:2502.10517
II.2 — the metric

Correct AND fast — fastp

Fraction of tasks where the generated kernel is both correct and at least p× faster than the PyTorch reference.

[01] Correct

Matches reference outputs within tolerance over multiple input shapes.

[02] Fast

Wall-clock speedup over PyTorch (eager or compiled), measured on the target GPU.

[03] Why p?

fast1 = strictly faster. fast2 = at least 2×. Asks "how good?", not just "good?"

II.3 — Dec 2024 baseline

The gap KernelBench made obvious

Correctness across frontier models

Speedup distribution — torch.compile wins most of the time

  • Frontier models could compile kernels. They rarely beat torch.compile.
  • Level 3 was brutal: ~20% success on full architectures.
  • Once the gap was easy to talk about, the field started moving.
Eval: Claude 3.5 Sonnet, GPT-4o, DeepSeek-Coder, Llama 3.1, others. Figures from Ouyang et al., 2024.

SECTION 02 / 06 · Eval4Kernel

What does correct even mean?

Verification, reward hacking, and the surprisingly high cost of just measuring time accurately.

● active: 02 / 06 — Eval4Kernel 3 problems most papers underrate
02.1 — the verification problem

Unit tests are not enough

"Verifying kernels for a mathematical operation on their own is not enough — we need verification at the level of the model pipeline, the training pipeline, the full train-eval pipeline." — Sakana AI, post-mortem on the AI CUDA Engineer
  • Sakana's AI CUDA Engineer (Feb 2025) shipped impressive numbers — until people noticed the kernels were exploiting test loopholes.
  • A softmax-1D kernel can pass a unit test by being wrong in a way the test doesn't probe.
  • Low-precision ops aren't deterministic. So "matches reference" is itself fuzzy.
  • Performance bounds — what's the actual ceiling? — remain dark arts even for human kernel engineers.
02.2 — reward hacking

Reward hacking is no longer hypothetical

  • Makora KernelHacks (Jan 2026): a taxonomy of 8 hack patterns mined from 2,500+ problem-kernel pairs. Released as a 1K-example dataset.
  • Dr. Kernel (HKUST + Sea AI Lab, Feb 2026): identifies a biased policy gradient in multi-turn GRPO and proposes TRLOO — turn-level reinforce-leave-one-out.
  • Common cheats: cached-compute reuse, mutating the input, moving real work to a non-default CUDA stream.
  • Bottom line: if your evaluator has a hole, RL will find it.
// observed hack patterns
  • Hardcode constants for known test inputs
  • Skip work the test doesn't observe
  • Time only the cached second call
  • Divert real work to async streams
  • Identity-pass on "trivial" shapes
  • Smuggle torch in the "kernel"
Makora Reward Hacks in CUDA Kernel Generation, Jan 2026 · Liu et al. Dr. Kernel, arXiv:2602.05885
02.3 — timing fidelity

Most "X% faster" claims don't control for noise

+21%
Mean latency increase under GPU contention
~30×
Variance blow-up under GPU contention
≈0%
CPU-load impact on mean latency
  • Standard Kernel's Feb 2026 benchmarking study: GPU contention quietly destroys your numbers.
  • Naive averages over noisy runs can fabricate or erase a 1.2× speedup.
  • Treat small wins skeptically unless the paper explicitly reports trimmed-mean / persistent-mode / contention-controlled numbers.
Standard Kernel benchmarking blog, Feb 2026.

04.3 — DICE

Diffusion enters the chat

  • DICE (Feb 2026): the first diffusion LLM for kernel generation.
  • Two-phase RL: an infilling stage on partial kernels, then end-to-end. Three scales (1.7B / 4B / 8B).
  • Beats AR baselines at the same scale. Non-autoregressive kernel gen isn't a curiosity anymore.
  • Kernels have structure diffusion exploits well — repeated tile patterns, parallel reductions, symmetric loops.
// architecture takeaway

If your generation target has strong local structure and parallel substructure, diffusion may outperform AR — even at smaller scales.

Open question: does this generalize to other systems-code domains (compilers, schedulers, layout selection)?

Bai et al. DICE: A Diffusion LLM for CUDA Kernel Generation, arXiv:2602.11715, Feb 2026.

SECTION 06 / 06 · Open Frontier

What's still hard.

Three problems I'd rather have a room of systems people argue about than try to settle myself.

● active: 06 / 06 — Open Frontier 3 open problems → leave with ideas
06.1 — abstractions

Are we generating in the wrong language?

  • Most systems still target raw CUDA / Triton. Triton has bank-conflict issues and is often stale on the latest hardware.
  • Training corpora over-index on whatever's available — and a lot of available CUDA on GitHub is bad CUDA.
  • 2026 winners point higher up the stack: CuTe, PTX, invariant-guided IRs, "Unified Sketch" representations.
  • Real question: should we design DSLs for LLMs? The right abstraction for a compiler-team is not the right abstraction for a model.
// pointing higher in 2026
  • CuTeGen — first CuTe-DSL agent (U. Toronto + Standard Kernel)
  • ARGUS — DSL + invariants + RL planner on MI300X
  • Standard Kernel — PTX-layer hybrid blending Triton, TileLang, ThunderKittens, CUTLASS
  • AKG / AscendCraft — Unified Sketch IR across DSLs
06.2 — non-stationarity

The target keeps moving

  • The kernels we care about today — single-GPU attention, GEMM, layernorm — are not the kernels that will dominate in 6–12 months.
  • Already on the horizon: multi-GPU kernels, MoE routing, sparse attention, speculative decoding, KV-cache compression, quantized attention.
  • "Solving KernelBench" is not the same as "solving kernel generation." The benchmark is a snapshot of an industry that re-prioritizes every release cycle.
  • Implication: we may need rolling benchmarks that retire and replace tasks as the field re-prioritizes.
What does it even mean for an automatic kernel-generation system to be "good"
when half its training distribution will be obsolete in a year?
06.3 — kernel gen ≅ arch search

Kernel gen is architecture search

— architecture choices and kernel choices are entangled

  • Mamba, RWKV, gated linear attention: the wall-clock speedup is in the architecture, not the implementation.
  • If we get really good at automatic kernels, the question shifts: what arch should we run, given what we can compile?
  • For known architectures: kernel gen at PTX or IR is a search over assembly variants. Closer to superoptimization than to software engineering.
  • For new architectures: hardware-first models, designed jointly with the kernels they'd compile to. Plausibly where this actually goes.
DISCUSSION

Where would you
spend the compute?

[A] Synthesize

Generate broader operator coverage with synthetic curricula — scale the training distribution.

[B] Post-train

RL with execution-grounded rewards inside hardened environments.

[C] Inference-time scale

Search at decode — agentic loops, evolution, memory — then post-train on the search traces.

[D] Teach the profiler

Train the model to use NCU well. Make profiler calls cheap and fast enough to be in the inner loop.
